# Rule Mapping Reference

Per `architecture.md` §1 (document-as-ground-truth convention): every
rule-check function in the engine cites which source document and section it
implements. This file is that cross-reference, kept up to date as each
module is built from Phase 2 onward.

Source documents are referenced by number and short name, matching
`phase0-knowledge-extraction.md` §1 (e.g. "doc 06/16/20" for the confirmed
single-source cluster, "doc 02" for `02-unified-logic-market-structure.md`).

Add one row per rule-check function as it's written. If a function
implements a judgment call rather than a directly-sourced rule (see Phase 0
§7), say so explicitly in the "Source" column instead of citing a document —
never attribute an invented rule to the material.

Wicks are ignored. | Phase0 §2.3. |
| `SNRZoneModule._detect_zones` (fresh → unfresh) | Doc 20 §14 (Fresh/Unfresh lifecycle) | A zone starts "fresh"; the first bar whose wick range touches the zone without fully closing through it flips the zone to "unfresh." | Phase0 §2.3. |
| `SNRZoneModule._detect_zones` (flip / RBS-SBR) | Doc 20 §15; universal RBS/SBR mechanic (docs 04-07, 10, 12, 13, 15, 16, 18, 20) | A bar whose *close* fully breaks through the zone flips its role (support↔resistance) and resets it to fresh in the new role. | Phase0 §2.3. |
| `SNRZoneModule.evaluate` (bias direction) | Doc 06/16/20 "A"-shape resistance rejection / "V"-shape support rejection (candle-close-based, not wick-based) | A bullish-bodied bar closing back above a support zone's bottom = bullish rejection; a bearish-bodied bar closing back below a resistance zone's top = bearish rejection. | Phase0 §2.3, §4. |
| `SNRZoneModule.__init__` (`min_gap_ratio` threshold) | Not source-stated — Phase0 §7 item pattern (judgment call, documented not invented) | A close→open gap must be ≥ a fraction of the instrument's average bar range to count as a zone. | Added after live validation showed the raw "any gap" rule producing sub-cent noise zones on Binance BTCUSDT 1h data. On continuous markets (Binance-style crypto) this module correctly detects few/no zones; that's expected, not a bug — see next row. |
| `SNRZoneModule` scope limitation (continuous markets) | Not source-stated — empirical finding from Phase 2 validation | This module's zone concept doesn't transfer to 24/7 continuous markets (crypto): live-data testing showed BTCUSDT close→open gaps sitting at 0.01–0.07% of average bar range even at the 99th percentile, vs. EUR/USD's real distribution (~9% at the 90th percentile, concentrated at the 21:00 UTC forex session rollover). | A different, swing-based zone-formation rule would be needed for crypto; deliberately not force-fit into this module. Candidate follow-up module. |

| `MarketStructureModule._structure_events` (BOS = continuation, CHoCH = reversal) | Doc 06 p.8, corroborated corpus-wide | A close that breaks a swing level in the direction of the current trend is a BOS (continuation); a close that breaks a swing level against the current trend is a CHoCH (reversal). | Phase0 §2.1. |
| `MarketStructureModule._structure_events` (break validity) | Doc 20 §§36-37 | A structure break requires the bar's *close* to fully clear the swing level — a wick beyond it doesn't count. | Phase0 §2.1, §7 item 3. |
| `MarketStructureModule` (MSS = CHoCH) | Phase0 §7 item 3 (judgment call, not source-stated as a single answer) | MSS is treated as a synonym for CHoCH, not a third distinct signal. | Doc 12 draws a three-way BOS/CHoCH/MSS distinction; most other documents use CHoCH and MSS interchangeably. Resolved by explicit decision, documented as such — see Phase0 §7. |
| `MarketStructureModule._find_swings` (`swing_strength` fractal rule) | Not source-stated | A bar is a swing high/low if it's strictly the most extreme high/low within `swing_strength` bars on each side (standard fractal/pivot convention; default 2 = "5-bar fractal"). | Added because BOS/CHoCH is used universally in the corpus but no document gives a swing-formation rule (doc 08 notes this gap explicitly). External, standard TA convention, not invented for this project specifically — documented per the project's rule. Validated live on both Binance BTCUSDT and Twelve Data EUR/USD across 1h/4h/1d without needing the kind of materiality-filter correction the SNR Zone module required — this concept doesn't have the same continuous-market blind spot. Extracted into the shared `analysis/swings.py` utility so `LiquiditySweepModule` reuses the same code (shared math, not module cross-talk). |
| `LiquiditySweepModule` (BSL/SSL definition) | Doc 08 §53 | BSL = liquidity above swing highs where retail sell-stops rest; SSL = liquidity below swing lows where retail buy-stops rest. | Phase0 §2.2 — the single most-corroborated mechanic in the whole corpus, though naming varies wildly (inducement/IDM/"Trap"/"TS" across different documents). |
| `LiquiditySweepModule._levels_and_sweeps` (sweep = wick-through + close-back) | Universal corpus mechanic ("stops get run before the real move"); distinguished from a genuine break via doc 20's full-body-close BOS/CHoCH test (used as the negative case here) | A level is swept when a bar's wick clears it but the bar's body closes back on the origin side — if the close also clears it, that's a structure break (market_structure.py), not a sweep. | Phase0 §2.2. |
| `LiquiditySweepModule.__init__` (`swing_strength=5` default, distinct from `MarketStructureModule`'s 2) | Not source-stated | Liquidity levels use a coarser swing-detection window than structure breaks. | Added after live validation: at strength=2, 15.4% of BTCUSDT 1h bars registered a sweep (~1 every 6 bars) — reads as routine noise, not the decisive event the corpus describes. The swept/level ratio (~70-75%) stayed constant across every strength tested, confirming this is a granularity choice, not a detection bug. The corpus names both minor (any swing) and major (PWH/PWL/PDH/PDL, EQH/EQL) liquidity without a formula distinguishing them — `swing_strength` is this module's stand-in lever until EQH/EQL clustering exists. |
| EQH/EQL clustering | Not implemented | — | Deferred, same reasoning pattern as SNR Zone's deferred Classic V/A: would need its own un-sourced "how close counts as equal" tolerance. Candidate follow-up, flagged not silently added. |
| `TrendlineConfluenceModule` (`TOUCH3_SIMPLE` variant) | Docs 06/16/20 p.32-33 | Enter only on the trendline's 3rd touch, with wick rejection — explicitly never on touch #2. | Phase0 §2.4, §7 item 4. |
| `TrendlineConfluenceModule` (`TOUCH3_ENGULFING` variant, partial) | Docs 04/05 | Touches #1 and #2 must each be engulfing candles, 2nd touch must break prior structure, 3rd touch requires HTF POI alignment, 45-60° trendline angle. | Phase0 §7 item 4 — both rules implemented as configurable variants since neither source corroborates the other. **Only 2 of 4 conditions implemented**: engulfing at touches 1 & 2, and the shared 3rd-touch-rejection logic. NOT implemented: (1) the 45-60° angle constraint — no principled numeric equivalent exists without knowing a chart's price/time axis scaling, which raw OHLC data doesn't encode; faking a normalization would misrepresent the source rule, not implement it. (2) "2nd touch breaks prior structure" and "3rd touch requires HTF POI alignment" — implementing these would require this module to depend on `market_structure.py`/`snr_zone.py`'s *signals*, which belongs in Layer 3 (aggregation), not Layer 2 (architecture.md's "no cross-talk" rule). Documented so Layer 3 knows to potentially recompose these three modules' outputs to approximate the full rule later. |
| `TrendlineConfluenceModule` variant rarity finding | Empirical, from live validation | `TOUCH3_ENGULFING` (even partial) produced 0-3 non-neutral signals across 300-bar replays on every one of 6 tested market/timeframe combinations, vs. 27-51 for `TOUCH3_SIMPLE`. | Checked the engulfing-pattern logic itself (standard textbook definition) — not a bug. The rarity comes from requiring genuine engulfing candles to coincide with swing-point bars at both anchor touches, a real if severe restriction, consistent with doc 04/05 presenting this as a stricter "very high probability" setup. Reported as a finding, not corrected by loosening the constraint to manufacture more signals. |
| `TrendlineConfluenceModule.__init__` (`touch_tolerance_ratio`, `max_line_age_bars`) | Not source-stated | A wick must come within `touch_tolerance_ratio` × average bar range of the extrapolated line to count as a touch; lines older than `max_line_age_bars` since their 2nd anchor are ignored. | Added after live testing showed old, no-longer-relevant trendlines producing spurious touches purely from long-distance extrapolation — same materiality-filter pattern as the SNR Zone module's `min_gap_ratio`. |
| `QMModule` (canonical QM definition) | Phase0 §7 item 2 (doc 10's taxonomy adopted over 3 other incompatible readings) | QM = the pattern, QML = the specific price level it marks. | An explicit editorial judgment call, not corpus consensus — see Phase0 §2.3, §7 item 2 for the 4 incompatible readings this resolved between. |
| `QMModule._match` (4-point sequence) | Doc 08 §5 (the clearest sequential statement in the corpus) | Bearish: 4 consecutive confirmed swings High→Low→High→Low where the 2nd high is lower than the 1st (failed new high = "Lower High") and the 2nd low breaks below the 1st ("Lower Low"). QML = the failed-high retracement price. Bullish is the mirror image. | Formalized from doc 08's prose description ("Bearish structure = HH→HL→LH→LL... entry at the retrace... that sits at the pre-break level") into a checkable 4-point rule. |
| QMM / QMC sub-variants | Not implemented | — | Named in docs 01/10 ("manipulation fake-break," "continuation fake-break") but never given a checkable distinguishing rule anywhere in the corpus — Phase 0's own review found these aren't consistently distinguished even within their source documents. Implementing a rule here would mean inventing one. Candidate follow-up if a real distinguishing rule turns up. |
| `QMModule` live validation | Empirical | 15-26 confirmed patterns and 36-56 retest signals per 300-bar window across 6 market/timeframe combinations, no calibration needed. | Validated cleanly on the first pass, unlike SNR Zone (needed a materiality filter) and Liquidity/Sweep (needed a coarser default). Not every module surfaces a problem — reported honestly either way. |
| `Aggregator._hard_gate` (HARD_GATE default preset) | Phase0 §4, §7 item 1 — modeled on docs 06/16/20 + 22 (Yanu Emmanuel F.'s hard AND-gate), the only fully self-consistent combination rule in the corpus | Combined signal only fires when active (non-neutral) modules unanimously agree; if they disagree, the result is CONFLICT, never averaged away. | This project's 5 modules don't map onto Yanu Emmanuel's specific named stages (bias/engulfing/structure/execution) — `_hard_gate` generalizes his AND-gate *philosophy* (nothing fires without full agreement) rather than literally reimplementing his 4 stages. Documented as a Phase 4 design choice, not a literal source implementation. |
| `Aggregator._hard_gate` (`min_agreeing_modules=2`) | Not source-stated | At least 2 modules must independently agree before a hard-gate signal fires — a single module's opinion alone isn't enough. | Added because the source model's "stages" don't correspond to this project's independent modules. Live pipeline testing showed this produces non-degenerate behavior (10-35% actionable rate depending on instrument) rather than always-neutral or always-firing. |
| `Aggregator._soft_score` (SOFT_SCORE alternative preset) | Phase0 §4, §7 item 1 — modeled on doc 01's "more confluence = stronger zone" framing | Each module's signed confidence (bullish +, bearish −) is averaged across all modules; sign gives direction, magnitude gives confidence. | Deliberately blends disagreement into one number, unlike HARD_GATE — that's the documented, intentional distinction between the two philosophies (architecture.md §3, Layer 3). |
| CONFLICT as a first-class aggregated state | architecture.md ground rule #0 ("surface [disagreement], don't average it away silently") | When active modules actively disagree under HARD_GATE, the result is CONFLICT, not NEUTRAL and not a majority-vote winner. | Live replay validation found this isn't a rare edge case: 19-26% of bars landed on CONFLICT across the two tested instruments — confirms this ground rule is operationally load-bearing, not just a nominal principle. |
| `ConfirmationLayer` (stop-loss rule) | Doc 02 §20 — the only fully explicit, generalizable SL rule in the corpus ("place stop loss at the nearest OB or liquidity zone") | Stop is the nearest swing point (`swings.py`) structurally opposing the trade direction, plus a small buffer. | Phase0 §7 item 4. Generalizes "nearest OB or liquidity zone" using the swing-point concept already shared across modules, rather than re-deriving OB detection separately. |
| `ConfirmationLayer` (take-profit rule) | Docs 08/11 §51, 13, and implied elsewhere — the single most-repeated TP idea in the corpus ("target = opposite liquidity") | Target is the nearest swing high (longs) / swing low (shorts) beyond entry — exactly where `liquidity_sweep.py`'s own BSL/SSL definition says liquidity rests, reused rather than re-derived. | Phase0 §7 item 5. |
| `ConfirmationLayer` (min 1:1.5 reward:risk gate) | Docs 01, 10 — the only quantified TP floor anywhere in the corpus | If the nearest opposing swing doesn't clear 1.5R, the next one out is tried; if none does, the signal is rejected as unconfirmed rather than force-fit into a trade. | Phase0 §7 item 5, enforced as a hard gate, not a suggestion. |
| `ConfirmationLayer.entry` (average of agreeing modules' `ModuleSignal.level`) | Not source-stated directly, but consistent with the corpus's own "entry at the refined level" language (e.g. doc 08 §51) | Entry price is the average of the specific price level(s) the agreeing modules anchored their signal to, not the current market close. | Added because architecture.md's Layer 6 calls for "entry as limit order," which needs a real reacted-to price, not an arbitrary proxy. Required adding `ModuleSignal.level` to all 5 Layer 2 modules. |
| **`SignalStateMachine` PENDING state — critical bug fix, not a cosmetic addition** | Not in architecture.md's original 4-state sketch (`IDLE → SIGNAL_ACTIVE → STOPPED_OUT \| TP_HIT → IDLE`) | A confirmed signal enters `PENDING` (a resting limit order) and only becomes `SIGNAL_ACTIVE` once a later bar's range genuinely trades through the entry price; unfilled orders `EXPIRE` after `max_pending_bars` (default 10, not source-stated). | The original 4-state version treated `entry` as filling *instantly* the moment a signal confirmed, regardless of where current price actually was. Since `entry` comes from `ModuleSignal.level` (sometimes several bars stale — e.g. `market_structure.py`'s `broken_level`, from a displacement candle that closed well past the level it broke), this let the backtest credit trades with price movement that happened *before* the theoretical entry. Live validation on BTCUSDT 1h found this producing an **11-for-11 (100%) win rate**, 8 of 11 trades resolving in exactly one bar. After the fix: 2/6 (33%) — a believable result for an uncalibrated system, not an impossible one. This is a more faithful reading of architecture.md's own "entry as limit order" language, not a deviation from the 4-state spec — an unfilled limit order is precisely a pending state. |
| `Backtester` (per-module directional-accuracy methodology) | Not source-stated | A module's non-neutral signal is scored correct/incorrect by whether price closed in the predicted direction `accuracy_horizon_bars` (default 5) bars later, relative to the signal bar's close. | The corpus never specifies how to score an individual module's correctness — only the combined system has SL/TP via `ConfirmationLayer`. A simple fixed-horizon directional-accuracy convention, chosen for this project and documented as such, not a trade-based (R-multiple) metric like the combined system uses. |
| `Backtester` walk-forward segmentation | architecture.md §5's warning ("multi-module systems can look deceptively strong in backtest purely from combining several factors — validate... out-of-sample specifically") | The full replay is split into sequential, non-overlapping chronological segments, each reported independently. | This project's reading of "walk-forward" for a rule-based (not fitted/trained) system: there are no parameters to re-fit per segment, so segmentation checks consistency across time rather than in-sample-vs-out-of-sample generalization in the ML sense. Live validation on 1000 bars (~41 days) of BTCUSDT and EUR/USD 1h found real segment-to-segment variance the aggregate number alone would have hidden — e.g. EUR/USD's overall +0.36R expectancy was driven almost entirely by one of three segments (+1.40R vs. -0.04R and -0.09R in the other two) — confirming this ground rule is operationally necessary, not just theoretical. |
| `market_structure` "still holding" signal — empirical finding, not a rule | Empirical, from `Backtester` live validation | Fires on nearly every bar once a trend is established (955 of ~960 possible bars scored in a 1000-bar BTCUSDT/EUR-USD backtest) but sits at 43-47% directional accuracy — at or slightly below a coin flip. | A genuine candidate for the "dead weight" component architecture.md's Layer 7 exists to find (§2 Layer 7: "this is how you'll eventually find out if one component is dead weight or actively hurting the combined signal"). `liquidity_sweep`'s sweep-event signal was the relative standout (58%/51%). Not acted on yet (e.g. by reweighting or removing the module) — reported as a finding for a future tuning decision, not silently fixed. |
| `SignalRegistry` idempotent per-bar processing (`api/state.py`) | Not source-stated — an API-layer correctness requirement, not a trading rule | The state machine only advances once per genuinely new closed bar per (source, symbol, timeframe), no matter how many times the endpoint/WebSocket is polled in between. | Without this, repeated polling within the same still-current bar would double-process transitions — e.g. re-triggering a fresh signal off stale data right after a STOPPED_OUT/TP_HIT/EXPIRED tick resets to IDLE on the next `process_bar` call, since that reset happens unconditionally at the top of the method. Verified live: two consecutive `/signals` calls for the same bar returned identical state, not a re-triggered transition. |
| `SNRZoneModule._detect_classic_zones` (Classic V/A, added post-Phase-2) | Docs 04, 05, 06, 08/11, 13, 15 — consistent description: "fast rejection (bullish candle right after touch) → buy bias" (doc 08 §7) | A confirmed swing low/high whose *next* bar closes back beyond the swing bar's own extreme, same-direction body — a checkable proxy for "fast rejection." Represented as a zero-width zone at the swing price, reusing the same fresh/unfresh/flip lifecycle as gap zones. | Deferred at Phase 2 because no swing-formation rule existed yet in the corpus (doc 08 itself notes the gap) — became implementable once `swings.py` was built for `market_structure.py`. Live validation found it fills exactly the gap flagged at the time: 29-42 classic zones detected per 200-bar window on BTCUSDT across 1h/4h/1d, where the gap-only version found zero (continuous-market blind spot, still present for gap zones specifically, now compensated for within the same module). |
| `ConfirmationLayer` SL/TP candidate pooling (revised) | Doc 02 §20 ("nearest OB or liquidity zone"); MSNR = the SNR Zone module in this corpus's own naming (Phase0 §5) | Stop-loss candidates now include SNR zone edges (`snr_zone.py`, opposing the trade direction) alongside raw swing points, not swing points alone; take-profit candidates now include actual BSL/SSL liquidity levels (`liquidity_sweep.py`) alongside swings. Raw swings stay in the pool as a fallback. | The original Phase 5 version approximated "nearest OB or liquidity zone" with generic swing points, disconnected from the actual SNR Zone/Liquidity modules. This revision reuses those modules' own (already-validated) detection directly — `detect_zones`/`detect_levels_and_sweeps` were promoted from private to public methods specifically so `ConfirmationLayer` could call them as a legitimate consumer. Re-ran the full backtest after this change: results stayed realistic (no regression toward the earlier 100%-win-rate bug), but genuinely shifted — BTCUSDT 1h improved (36.84%→38.46% win rate, +0.05R→+0.24R expectancy), EUR/USD 1h worsened (36.84%→26.92%, +0.36R→-0.03R). Reported plainly: different specific SL/TP price levels produce different trade outcomes, which is expected, not a defect — the change is motivated by fidelity to the source material, not by which backtest number it produces. |
| `CRTModule` (3-candle PO3 model) | Doc 02 §5, §19-20; corroborated in docs 07, 09 | Candle 1 = Accumulation range [CRL, CRH]; candle 2 = Manipulation, a liquidity sweep of that range; candle 3 = Distribution, the real move opposite the sweep direction, confirmed by its close. A candle 2 sweeping both sides (outside bar) or neither is not a clean setup — treated as neutral, not resolved with an invented tie-break. | Phase0 §2.4. "Phase 3 confirmation" (doc 02's phrase) formalized as: candle 3's close continues past candle 2's close *and* closes back on the side of the range the sweep denied. Doc 02 §20's own SL/TP rule for this pattern ("stop at nearest OB/liquidity zone... target = next structural level or BOS") is not duplicated in this module — it's the same rule already generalized into `ConfirmationLayer`, which applies to every module's signals uniformly. Live validation: 58-91 non-neutral calls per 297-window replay across 6 market/timeframe combinations, roughly balanced bull/bear (no directional skew), all three logical outcomes (confirmed / ambiguous sweep / unconfirmed) observed firing correctly. Added to `default_pipeline`; post-addition backtest shows 48.4% standalone directional accuracy on BTCUSDT 1h, similar to most other modules (near a coin flip, `liquidity_sweep` remains the standout at 58%). |
